1. What Skout AI is

Skout AI is a GTM (go-to-market) operating system. In one workflow a user can: find prospects in a large corpus, qualify them with AI against their Ideal Customer Profile (ICP), enrich contact data (email, firmographics, phone) on demand, organize prospects into lists, and push them to a CRM.

The core thesis: company data is a commodity; the value is the intelligence layer. Skout builds a cheap, broad prospect corpus itself (the scrape pipeline) and only spends money on paid third-party APIs when a user shows intent (clicks "enrich") or a lead scores high enough to deserve the most expensive data (phone numbers are gated behind a high lead score).

2. Architecture & the two-tier data model

Everything in Skout flows through two tiers. Understanding this one picture explains every feature, every credit charge, and every setting.

TIER 1 — CORPUS (global, cheap, read-only)   TIER 2 — WORKSPACE (per-tenant, owned, paid)
┌─────────────────────────────┐              ┌──────────────────────────────────┐
│ OpenSearch "prospects" index │   activate   │ PostgreSQL (scoped by workspace)  │
│  • scraped records           │  ─────────▶  │  • prospect_activations (snapshot)│
│  • manual entries            │   (free)     │  • lists / list_members           │
│  • shared by ALL workspaces  │              │  • enrichment_jobs/results/attempts│
│  • powers SEARCH             │              │  • prospect_scores                │
│  ~5,300 demo rows if no OS   │              │  • icp / credits / crm / byok     │
└─────────────────────────────┘              └──────────────────────────────────┘
ConceptMeaning
CorpusGlobal pool of prospects in OpenSearch. Read-only via search. No single workspace owns it. If OPENSEARCH_URL is unset, a ~5,300-row in-memory demo corpus is used instead.
ActivationThe moment a prospect is copied into a workspace (prospect_activations). Free, no external spend. Creates a JSON snapshot the workspace owns and can enrich/score.
EnrichmentOn-demand paid API calls (the PAL waterfall) that fill in email / firmographics / phone on an activated prospect.
ScoringAI qualification of a prospect against the workspace ICP (0–100), with a band and outreach-readiness label.
Rule of thumb: search reads the global corpus; everything you "own" lives in Postgres as an activation. Paid actions only happen on activated prospects in your workspace.

4. Feature catalog (UI + backend)

4.1 Sign-in & onboarding FREE

From the UI

  • Sign in at /sign-in with Google (Clerk). Already-signed-in users skip straight to the app.
  • After login the app lands on /auth/callback, which checks your ICP: no ICP → the 3-step ICP wizard (/onboarding/icp); ICP already set → /dashboard.
  • The ICP wizard has a progress bar and 3 steps: (1) Industries, (2) Geo & seniority, (3) Company size. Buttons: Back, Next, and Save & go to dashboard.

Backend logic

  1. Clerk issues a JWT; the Fastify auth plugin verifies it on every request.
  2. resolveOrProvisionUser() resolves the user by clerk_user_id (fast path) or email (back-fill).
  3. First-ever login provisions, in one transaction: a workspaces row, a workspace_members row (role owner), a credit_balances row seeded with 500 starter credits, and a credit_transactions ledger row (action provision, +500).
FieldMeaning
clerk_user_idSSO identity from Clerk
workspace_idTenant boundary — every other table is scoped by it
roleowner / admin / member (first user = owner); gates the scrape admin pages
Saved in: Postgres — users, workspaces, workspace_members, credit_balances, credit_transactions.

4.2 ICP — Ideal Customer Profile FREE

From the UI

  • Set up via the wizard (/onboarding/icp, stepped) or edit any time at ICP settings (/settings/icp, all fields on one page).
  • Wizard fields: Industries (chips), Countries + Seniority (chips), Min/Max employees (number inputs).
  • If you try a credit action (enrich) without an ICP, the app redirects you to /settings/icp?return=… with a "configure your ICP first" message. Search and Score show inline warnings instead of redirecting.

Backend logic

GET /workspace/icp reads the config; PUT /workspace/icp upserts the config JSON and bumps a version integer (first save = 1, each update = +1).

4.4 Prospect search PAID — 1 credit / live page

From the UI

  • At /prospects/search: a search box (placeholder "e.g. VP Sales, fintech, Series B…", 400ms debounced) plus a left filter sidebar with ~24 collapsible sections (person, company, title, location, contact-details, intent, funding, tech, headcount, hiring, etc.). On mobile, filters open in a bottom sheet via a Filters (n) button.
  • Results card: header shows "Showing X–Y of Z · cached|live"; rows-per-page 10/25/50; Select all / Clear all. Each row has a checkbox, a clickable name (opens a detail side-sheet), badges, and per-row actions.
  • Per-row actions: Details (slide-over), Score (2 credits, disabled until ICP set; turns into a score badge with reasoning tooltip), Enrich (1 credit; shows spinner, then email + status inline, or a Retry on failure).
  • Bulk add: selecting rows reveals a bar — pick a list from a dropdown and click Add to list.
  • States: 5 skeleton rows while loading; "No prospects found" empty; dismissible "Search unavailable" error with retry.

Backend logic

  1. POST /search/prospects builds a cache key: search:{workspaceId}:{sha256} where the hash covers a stably-serialized {query, filters, page, pageSize} (filter key order doesn't matter).
  2. Cache hit (Redis): returns instantly with cached: true, creditsUsed: 0. TTL = SEARCH_CACHE_TTL_SECONDS (default 300s). Falls back to an in-process map if Redis is down.
  3. Cache miss: deduct SEARCH_CREDIT_COST (default 1) → build an OpenSearch bool query (free-text multi_match on name/title/company/industry in must; all structured filters in filter; sort by updatedAt desc) → cache the page.
  4. If OPENSEARCH_URL is unset or OpenSearch errors, it transparently falls back to the demo corpus.

Dedupe & pagination: excludeDuplicates and maxPerCompany are post-processing filters. When either is on, search scans OpenSearch in batches (up to ~20,000 docs), applies dedupe, then paginates — so totals and pages stay correct after de-duplication.

Response fieldMeaning
results[]Page of prospect summaries
totalMatch count (after dedupe when applicable)
cachedtrue = served free from Redis
creditsUsed0 (cached) or 1 (live)

Filter inventory (40+ across groups): Person — fullName, jobTitle, department, seniority, jobFunction, email/phone/linkedIn availability. Experience — years at company / in role / total, previousCompany, founded-year range, headcount growth, email provider, min intent score. Company — name, domain, keyword, industry, sub-industry, country/state/city, employee range, stage, funding round, revenue range. Signals — contactSignals[] and companySignals[] (OR-matched nested), single signal, tech stack. Hiring — currentlyHiring, hiringDepartments[]. Dedupe — excludeDuplicates, maxPerCompany (1–10).

Saved in: nothing persisted except the credit deduction (ledger) and the Redis cache entry. Search is read-only over the corpus.

4.5 Add prospect (manual) FREE

From the UI

  • At /prospects/add: a multi-card form (Contact, Company, Revenue & funding, Hiring & technology). Only Full name is required. Success screen offers Enrich this prospect and Add another.

Backend logic

POST /prospects/manual normalizes the domain (lowercase, strip scheme/www/path/port), generates deterministic IDs (generateProspectId = sha256 of domain + hashed email; generateCompanyId = sha256 of domain), and upserts directly into OpenSearch (bulk index with _id = prospectId). It becomes searchable immediately but is not workspace-owned until activated. Returns 503 if OpenSearch isn't configured.

Saved in: OpenSearch only (no Postgres write until activation).

4.6 Activation FREE

From the UI

There's no dedicated "activate" button — it happens implicitly whenever you add prospects to a list (from search, or by activating a smart list). The prospect is now "owned" by your workspace and can be scored/enriched.

Backend logic

EnrichmentService.activate() upserts one prospect_activations row per prospect — no external API spend. The snapshot JSONB holds identity fields and is later merged (JSONB ||) with enrichment output, so re-enriching never wipes prior data.

Saved in: Postgres — prospect_activations (snapshot JSONB).

4.7 Contact enrichment — the PAL waterfall PAID — ~1 credit / successful step · flagship

From the UI

  • At /enrichment: an enrich form — Company domain (required), Full name, Job title, Known email, LinkedIn URL — plus field toggles: Firmographics, Email finder, Email verify, Phone (score gate). Default selected: company + email + validation. The hint reads "Add a LinkedIn URL for better phone match rates."
  • Click Run enrichment → Running… → Run again. An inline result panel shows status, credits used, a View job link, and Email/Phone rows with a verification-source line (e.g. "Verified via MillionVerifier").
  • Recent jobs (right column) auto-refreshes every 2s while jobs are running; failed jobs show a Retry button.
  • The Job detail sheet shows: status + trigger + credits, a credits breakdown, a timeline (Queued / Started / Completed), per-field Results (provider badge, confidence %, verification source, "providers tried"), and a per-step Provider attempts log (provider, operation, status, latency).
  • Enrichment requires an ICP — without one the page redirects to /settings/icp?return=/enrichment first.

Backend logic (enrichProspect)

Runs synchronously inside the HTTP request (the job is already completed/failed by the time the API returns 202):

  1. Ensure the prospect is activated (free).
  2. Credit pre-check (balance must be ≥ 1).
  3. Create the job (queued) then immediately mark running with a distinct startedAt.
  4. Resolve the lead score for the phone gate: use the stored prospect_scores.score if present, otherwise score now (which costs 2 credits and requires an ICP).
  5. Build the per-workspace PAL engine (BYOK keys first, then platform keys).
  6. Run the waterfall (see section 5), deduct credits for successful paid steps, merge results into the activation snapshot, persist results + attempts, mark completed.

The four stages, in order:

Step 0  internal_graph   FREE   reuse cached company/email from the activation snapshot
Step 1  firmographics    PAID   PDL → RevenueBase → Explorium → Coresignal
Step 2  email find       PAID   Hunter; else pattern-gen (firstname.lastname@domain, conf 0.4 — free)
Step 3  email validation PAID   MillionVerifier → ZeroBounce → NeverBounce (→ Hunter-verify fallback)
                                 email becomes "primary" ONLY if status === valid
Step 4  phone            PAID   GATED: lead score must be > 80 (ENRICHMENT_PHONE_SCORE_GATE)
                                 Datagma → Kaspr → Lusha → ContactOut → Cognism

Credit billing: each successful paid step adds "quarters" (workspace BYOK = 3, platform = 4); total credits = ceil(quarters / 4). Free steps (internal_graph, pattern-gen, gate skips, misses/errors) cost nothing. So four platform steps = 4 credits; four BYOK steps = 3 credits.

Bulk enrich (from a list): POST /lists/:id/enrich creates an enrichment_batches row and enriches each member sequentially (trigger = bulk); the UI polls GET /enrichment/batches/:id for done/failed counts.

Saved in: Postgres — enrichment_jobs (status, timestamps, creditsUsed, fieldsRequested, trigger), enrichment_results (one row/field), enrichment_attempts (one row/provider call), prospect_activations.snapshot (merged primary email/phone/company), credit_transactions (action enrichment).

4.8 AI lead scoring PAID — 2 credits / prospect

From the UI

  • Score a single prospect from a search row (button becomes a colored score badge, e.g. "72 · High", with the reasoning as a tooltip).
  • Score all on a list detail page (costs 2 × member count) — shows progress "Scoring prospects against your ICP…" and a final summary with skipped count.
  • Scoring is disabled / warns if no ICP is configured.

Backend logic

Flow: load ICP (reject with 400 ICP_NOT_CONFIGURED if empty) → deduct 2 credits (ai_score) → call the Python AI service POST /v1/score → persist to prospect_scores.

LLM path (when OPENAI_API_KEY is set on the Python service): it always computes a heuristic baseline, then asks the model (gpt-4o-mini via LiteLLM, JSON response) to refine it using the full prospect + ICP + intent-signal map. Any error falls back to the baseline.

Heuristic path (no OpenAI key, or AI service unreachable): deterministic math.

4.10 Smart lists FREE to run/preview

From the UI

  • Run previews matches live (up to 10 shown, with total and a "+N more" note); a Demo data badge appears if OpenSearch isn't connected.
  • Activate turns matches into a real list — choose New list (default name "{smart list} — {date}") or Existing list — then Create list (N) / Add to list (N).

Backend logic

Filters saved as JSON in smart_lists. Run (POST /smart-lists/:id/run) executes the filters against OpenSearch (read-only, limit 1000) or the demo corpus, and updates last_run_count. Activate (POST /smart-lists/:id/activate) runs the filters, activates every match, and creates or extends a static list.

Saved in: Postgres — smart_lists (filter JSON). Activation writes prospect_activations + lists + list_members.

5. The enrichment waterfall in depth

This is the most important backend mechanism. Each stage tries providers in order and stops at the first usable result. For every provider type, your workspace (BYOK) key is tried before the platform key.

5.1 Step 0 — internal graph (free cache reuse)

Before any paid call, the engine reuses data already on the activation snapshot:

  • Company cache: if the snapshot already has company data, it's used directly (provider internal_graph, isPrimary) and the entire firmographics loop is skipped.
  • Email cache: a cached email is reused only if its stored status is valid (provider internal_graph, confidence 1), skipping the paid finder.
  • A user-supplied "Known email" likewise skips the finder (validation still runs if requested).

5.2 Step 1 — Firmographics

Order: PeopleDataLabs → RevenueBase → Explorium → Coresignal (each: workspace key, then platform key). First non-null wins. If no live keys, a stub returns nothing.

ProviderAPIReturns
PeopleDataLabsGET /company/enrich?website=&name= (header X-Api-Key)name, industry, employeeCount, HQ country/city, founded
RevenueBasePOST /v2/organization/resolve (header x-key)name, HQ country/city
Exploriumtwo-step POST /businesses/match then /firmographics/enrichname, industry, employeeCount (range-parsed), HQ
CoresignalGET /company_multi_source/enrich?website= (Bearer)name, industry, employeeCount, HQ, founded

5.3 Step 2 — Email find

Provider: Hunter (GET /v2/email-finder; returns email + confidence = score/100; has special handling for synthetic LinkedIn-capture domains). If Hunter misses and a full name is present (and the domain isn't synthetic), a pattern guess is generated — the first of a ranked list (e.g. firstname.lastname@domain) with a fixed confidence 0.4. Pattern-gen is free (not billed).

5.4 Step 3 — Email validation

Order: MillionVerifier → ZeroBounce → NeverBounce (workspace then platform each). If none of those keys exist, a Hunter email-verifier fallback is used. Each maps vendor statuses to a canonical verdict: valid / invalid / catch_all / risky / unknown.

The "primary" rule: the found email is promoted to isPrimary (and written to the snapshot) only when the verdict is exactly valid. Anything else is recorded but not treated as the canonical email. Cache reuse later also only trusts valid.

5.5 Step 4 — Phone (gated)

Phone is the most expensive data, so it's locked behind the lead score:

  • Gate: phone runs only if score > ENRICHMENT_PHONE_SCORE_GATE (default 80, i.e. score must be 81+). If score ≤ gate, a phone-gate / score-gate attempt is logged as skipped with a reason, and no provider is called.
  • Re-scoring: if firmographics added industry/country/employee-count, the engine can re-score before the gate, so newly-discovered data can unlock phone within the same job.
  • Name gate: even if the score passes, no full name → skipped.
  • Order: Datagma → Kaspr → Lusha → ContactOut → Cognism (workspace then platform each).

5.6 Attempts, status & job lifecycle

Every provider call appends an attempt with: order, provider, operation, status (ok / miss / error / skipped), latencyMs, and an optional detail. This powers the per-step timeline in the job detail sheet. Job states move queued → running → completed | failed, each with its own timestamp (queuedAt, startedAt, completedAt).

7.4 Credits balance

Credits gate every paid action. The UI is proactive: before spending, it checks the cached balance and, if short, opens the buy-credits modal without calling the API. The backend is the safety net — insufficient balance returns 402 insufficient_credits with required / available. Batch operations pre-check the total cost and fail fast before spending anything.

8. Credit economics

Free:    activation, internal-graph cache hits, pattern-gen email guess,
         cached search, phone-gate skips, all failed/missed provider calls
Paid:    search (1 / live page), score (2), each successful enrichment step (~1),
         HubSpot export (1 / contact)
Cheaper: BYOK steps bill at 75% of platform rate (3 quarters vs 4)

The model is deliberately "build cheap, spend on intent": the corpus is free to search broadly; money is only spent when the user activates and enriches a specific prospect, and phone — the most expensive data — is locked behind a high lead score.
